# デモの手順とデモ用データ

ハッカソンのデモ用の手順です。デモには、問題を意図的に仕込んだ**合成論文** `demo/demo_paper_ja.pdf` を使います（本文・著者・データはすべて架空。参考文献だけは実在の公開論文の書誌情報）。未発表の論文はデモに使いません。

合成論文は `make demo-paper`（`scripts/make_demo_paper.py`）で作り直せます。

## デモ用データ

| ファイル | 内容 |
|---|---|
| `demo/demo_paper_ja.pdf` | 問題を9か所仕込んだ合成論文（下の「仕込んだ問題」） |
| `demo/demo_guide_rules.md` | 架空の学会の投稿の手引き（ルール資料。「ルール」の画面で登録する） |
| `demo/demo_lab_review.md` | 架空の過去の査読コメント・回答・添削メモ（専門知識。「専門知識」の画面で登録する） |

このデモ論文の解析結果（解析ID A-e8f312ab9445、下の「試行の結果」）は `core/sample/` に収めてあり、ワーカーの起動時に「（例）」として解析の一覧に加わる（無いときだけ取り込む）。例の論文は削除できない。

## 事前の準備

1. `make up` で全サービスを起動し、`make check-api` で おいとまAPI に繋がることを確かめる
2. 「ルール」の画面で `demo_guide_rules.md` を登録し、抽出されたルールを確認して承認する（10件前後。提出方法・ページ数は「参考」になる）
3. 「専門知識」の画面で `demo_lab_review.md` を登録する（過去の指摘3件と、研究室のルール2件が取り出される。ルールは「ルール」の画面で承認する）
4. 解析には時間がかかるので（下の「試行の結果」）、**デモの前に1回解析を済ませておき**、当日はその結果を見せながら、もう1回をライブで走らせる
5. 外部検索のモードは `standard`（既定）のままにする（書誌の照合が自動で走る）

## デモの流れ（約5分）

| # | 画面・操作 | 見せるところ |
|---|---|---|
| 1 | トップページで `demo_paper_ja.pdf` をアップロードし、解析を開始する | 進捗バー・経過時間。工程（構造化 → 段落内 → 段落間 → 引用の検証）ごとに進む |
| 2 | 解析中のダッシュボードを開く | 確定した指摘から順に表示される（3秒ごとに更新） |
| 3 | 事前に解析した結果のダッシュボードを開く | 左上の総指摘数と重大度の内訳、カテゴリ別・セクション別のグラフ、「表で見る」「CSV」 |
| 4 | 指摘一覧から「論理の飛躍」の番号をクリック | PDF ビューアで該当箇所に下線、指摘・理由・改善案。2クリックで到達 |
| 5 | 引用の指摘（書誌の誤り・引用内容の不一致）を開く | 参考文献[3]の発行年の誤り（正しい書誌を改善案として提示）、[2]が主張を支えていないこと |
| 6 | 指摘を「対応済み」「却下（理由つき）」にする | 件数から却下が除かれる。注釈付きPDFにも反映 |
| 7 | 「注釈付きPDF」を開く | 種類ごとに形と色が違う注釈（下線・網掛け・枠）と、余白の番号ラベル |
| 7b | 「ルール違反」「専門知識」の指摘を開く | 投稿の手引きの「結論で新たな主張をしない」への違反（波線）、過去の査読で「1つの病院のデータから一般化」と指摘されたのと同じ問題（点線の枠） |
| 8a | 「承認キュー」を開く | 定義なしで使った専門用語「アイソクローン」の照会が、承認待ちになっていること。承認するまで学外には出ない（承認すると、その1語だけが送られる） |
| 8 | 「外部通信ログ」を開く | 学外に出たのは参考文献の書誌情報（タイトル・著者・年・DOI）だけで、原稿の文は出ていないこと |

締めの一言：「論文の本文は、学内の おいとま と、このサーバーの中から一歩も出ていません」

## 試行の結果

2026-10-13、`make up` の構成で、アプリから最終版の `demo/demo_paper_ja.pdf` を解析した（解析ID A-e8f312ab9445。未知の用語の照会を加えた版）。

- 所要時間：約10分（おいとまAPIへのリクエスト80回）
- 指摘：13件（重大2、要修正11）。仕込んだ9か所のうち8か所を検出（前の版と同じく「主語と述語のねじれ」を見逃した）
- 未知の用語の照会：「アイソクローン」「平均絶対誤差」「通院」の3語が承認キューに積まれた（承認するまで学外には出ない）。
  最初の試行（A-7a70606ca54f）では、タイトルの語（オンデマンド交通・配車計画）と引用の付いた既存のモデル名（LSTM など）が選ばれたため、
  タイトルに含まれる語と、引用の付いた文に出てくる語を除くようにした（最初の試行の5語は却下した）

前の版（「アイソクローン」の文を加える前）の試行（解析ID A-11196770680f）：

- 所要時間：約12分（14段落、おいとまAPIへのリクエスト67回）。ほかの試行では10〜16分
- 指摘：14件（重大3、要修正10、提案1）。仕込んだ9か所のうち8か所を検出（「主語と述語のねじれ」を見逃した）
- 学外への通信：書誌の照会など（キャッシュに無いものだけ送る）。原稿の文は送っていない（外部通信ログで確認）

仕込んでいない箇所への指摘（デモで質問されたときの説明用）：

| 指摘 | 説明 |
|---|---|
| Transformer[4]・ランダムフォレスト[1]の引用内容の不一致 | 引用先のアブストラクトには「時系列の予測」「交通需要の予測」の話が無いため。原典の手法を引用しているだけなので、利用者が「却下（理由：手法の原典の引用）」にする例として使える |
| 「それが大きい地区ほど」への論理の飛躍、朝の通院の時間帯の短縮への論理の飛躍 | 仕込んだものではないが、本文に根拠（地区の割り当ての方法、時間帯別のデータ）が無いのは事実 |
| 実験・関連研究の節の役割違反 | 仕込んだ「前提と根拠の不一致」「接続の断絶」と同じ箇所を、別の観点からも指摘したもの |

結果は試行ごとに少し変わる（自己一貫性の多数決でも、思考モデルの判定にはばらつきがある）。読みやすさの指摘（指示語の曖昧さ・主語と述語のねじれ）は、論理の指摘より検出が安定しない。

### ルール・専門知識の試行（2026-10-13、デモ論文に対して単独で実行）

- ルール：手引きから10件を抽出（略語・図表の2件は組み込みの機械判定に統合）。LLM 判定で「関連研究で本研究との違いを明示していない」「結論で新しい主張をしている」などを指摘
- 専門知識：過去の指摘3件・研究室のルール2件を取り出した。類似箇所は、要旨・はじめに・考察の過度な一般化と、実験節の「運転手の回答から利用者の満足度を結論づけている」の計4段落で検出（誤検出なし。判定は思考モデル）
