# Google でのログインの設定と運用

SI-NSA は、岡山大学の Google アカウント（`okayama-u.ac.jp` と、そのすべてのサブドメインのメールアドレス）でログインできます。ログインしていない利用者（ゲスト）は、共通デモの閲覧だけができます。

この文書は、Google Cloud での設定、起動、動作確認、運用（Cookie・鍵・セッション）、ログインできないときの調べ方、デモのときの設定、開発メンバーが動作を確かめる手順をまとめたものです。初めて試す開発メンバーは、第10章で自分の状況（Google の設定なしで試すか、共有のサーバーで試すか）を確かめてから、第3章の手順で確認してください。設計の詳細は [access-control-design.md](access-control-design.md) の第I章にあります。

---

## 1. 仕組みの概要

```
ブラウザ ──(http://localhost:8080)──> web（nginx）
                                      ├─ /api/  → core（要求ごとに authn でセッションを確かめ、署名つきの主張だけを渡す）
                                      └─ /auth/ → authn ──> auth_proxy ──> Google（OIDC のエンドポイントだけ）
ブラウザ ──(ログインの画面だけ)──> accounts.google.com
```

- ログインは、Google の OpenID Connect（認可コードフロー＋PKCE）で、サーバー側（`authn`）が処理します。ブラウザに Google の JavaScript は読み込みません（CSP も変えていません）
- Google に求める情報は `openid email` だけです（氏名・プロフィールは求めません）
- `authn` は、論文・解析結果・データベース・監査ログのボリュームをマウントせず、学外へは `auth_proxy`（Google の3つのホストだけを許可）経由でしか通信できません。**論文や解析結果は Google に送りません**
- ログインを受け付けるのは、ID トークンの署名・発行者・宛先・期限・nonce を確かめたうえで、次の両方を満たすアカウントだけです
  - 確認済みのメールアドレス（`email_verified` が true）のドメインが `okayama-u.ac.jp` かそのサブドメイン
  - 組織のドメイン（`hd`。Google Workspace のアカウントにだけ付く）が `okayama-u.ac.jp` かそのサブドメイン
  - 両者が同じドメインであることまでは求めません（例：メールが `s.okayama-u.ac.jp`、`hd` が `okayama-u.ac.jp` でもよい）。学生・教職員の区別、学部・研究室による制限はしません
- 利用者は Google の `sub`（アカウントごとに変わらない ID）で識別します。メールアドレスは表示用で、データの持ち主の判定には使いません。同じメールアドレスでも、別の Google アカウント（別の `sub`）は別の利用者です

## 2. Google Cloud での設定（手作業）

Google Cloud の設定は、管理者が手作業で行います（このリポジトリのツールや AI からは操作しません）。**課金の設定（請求先アカウント）は不要です。** 有料の API は有効にしないでください。

> Google Cloud Console の画面や名称は変わることがあります。以下は 2026年10月時点の「Google Auth Platform」の画面に沿った手順です。表示が違う場合は、同じ意味の項目を選んでください。

### 2.1 プロジェクトを作る

1. https://console.cloud.google.com/ を開き、**大学の Google アカウント**でログインします
2. 画面上部のプロジェクトの選択 →「新しいプロジェクト」
3. プロジェクト名：`si-nsa`（任意）。組織：`okayama-u.ac.jp`（選べる場合）。請求先アカウントは設定しません
4. 作成したプロジェクトを選びます

> 大学の Google Workspace の管理者が、学内アカウントでのプロジェクトの作成を制限している場合があります。作成できない場合は、情報統括センターなどの管理者に相談してください。

### 2.2 OAuth 同意画面（ブランディング・対象）を設定する

1. 左のメニュー（または検索）から「**Google Auth Platform**」を開き、「開始」を押します
2. **アプリ情報**：アプリ名 `SI-NSA`、ユーザー サポートメール：自分の大学のメールアドレス
3. **対象（Audience）**：開発・動作確認の間は**内部（Internal）**にします（現在の設定）
   - 内部では、プロジェクトが属する Google Workspace の組織（大学の Workspace の契約1つ分。プロジェクトの選択画面に組織名が表示される）のアカウントだけがログインでき、Google の審査もテストユーザーの登録も要りません
   - 学生のアカウント（`s.okayama-u.ac.jp`）と教職員のアカウント（`okayama-u.ac.jp`）が別の組織で管理されている場合、内部ではプロジェクトを作った側のアカウントしかログインできません
   - 学生と教職員の両方が使えるようにする（デモ・全学での利用）ときは、第9章の手順で**外部（External）**にして公開します
4. **連絡先情報**：自分の大学のメールアドレス
5. 規約に同意して作成します

### 2.3 スコープ（データアクセス）

「データアクセス」で、次の2つだけを追加します（どちらも機密性の高くないスコープです）。追加しなくても動きますが、同意画面の表示をそろえるために登録しておきます。

- `openid`
- `.../auth/userinfo.email`（メールアドレスの表示）

`profile`、Google ドライブなどのスコープは追加しないでください。

### 2.4 OAuth クライアント ID（ウェブ アプリケーション）を作る

1. 「**クライアント**」→「クライアントを作成」
2. アプリケーションの種類：**ウェブ アプリケーション**
3. 名前：`SI-NSA local`（任意）
4. **承認済みの JavaScript 生成元**：空のままで構いません（ログインはサーバー側で処理するため）
5. **承認済みのリダイレクト URI**：次を1行だけ登録します（コピーして貼り付けてください）

   ```text
   http://localhost:8080/auth/callback
   ```

   - `localhost` と `127.0.0.1` は Google にとって別の URI です。SI-NSA の既定は `localhost` なので、`127.0.0.1` は登録しません
   - 末尾の `/` の有無、ポート番号も完全に一致させます
6. 「作成」を押すと、**クライアント ID** と**クライアント シークレット**が表示されます。シークレットは作成時にしか表示されないことがあるので、その場で JSON をダウンロードするか、次の手順で `.env` に記入してください

### 2.5 クライアント ID とシークレットを安全に設定する

SI-NSA を動かすマシンの、リポジトリの `.env` に記入します（`.env` は Git の管理外です）。

```bash
cp .env.example .env    # まだ無い場合だけ
chmod 600 .env
# エディタで .env を開き、次の2行に値を記入する
#   GOOGLE_OAUTH_CLIENT_ID=<クライアント ID>（…apps.googleusercontent.com で終わる）
#   GOOGLE_OAUTH_CLIENT_SECRET=<クライアント シークレット>
```

- シークレットは**チャット・AI ツール・Issue・コミットに貼り付けない**でください。Claude Code などを起動したまま `.env` を開かないでください
- シークレットは `authn` のコンテナにだけ渡されます（`core` などには渡しません。`tests/unit/test_compose_structure.py` で確かめています）。ログにも出しません
- ダウンロードした JSON は、`.env` に記入したら削除してください
- シークレットが漏れた疑いがあるときは、Google Auth Platform の「クライアント」で新しいシークレットを追加し、`.env` を書き換えて `docker compose up -d authn` で再起動してから、古いシークレットを無効にします

必要に応じて、次の値も `.env` で変えられます（既定のままで動きます）。

| 変数 | 既定 | 内容 |
|---|---|---|
| `GOOGLE_OAUTH_REDIRECT_URI` | `http://localhost:8080/auth/callback` | Google に登録したリダイレクト URI と**完全に同じ**値 |
| `MONGAI_ALLOWED_EMAIL_DOMAINS` | `okayama-u.ac.jp` | 許可するドメイン（カンマ区切り。サブドメインも許可）。`authn` と `core` の両方が使う |
| `MONGAI_SESSION_HOURS` | `8` | ログインの有効期間（時間） |
| `MONGAI_SESSION_IDLE_MINUTES` | `120` | 操作しないとログインが切れるまでの時間（分） |

## 3. 起動と動作確認

### 3.1 起動

```bash
make build
make up            # 本番相当の構成（authn と auth_proxy も起動する）
```

設定だけを変えたとき（`.env` の書き換え）は、`docker compose up -d --wait` で `authn` が作り直されます。

`git pull` やブランチの切り替えでコードが変わったときは、イメージを作り直してから起動します（`make up` はイメージを作り直しません。古いイメージのまま動くと、直したはずの不具合が残ります）。

```bash
docker compose -f compose.yaml up -d --build --wait
```

起動後、`docker compose logs authn` に次の行が出ていれば、Google のクライアントが設定されています。

```text
INFO authn 認証サービスを起動（鍵 authn-…、コールバック http://localhost:8080/auth/callback）
```

「Google のクライアント…が未設定」という警告が出ている場合は、`.env` の値を確かめてください（未設定の間は、全員がゲストになります）。

### 3.2 動作確認の順序

ブラウザで **http://localhost:8080** を開き（`127.0.0.1` ではなく `localhost`。古い画面が出たら Ctrl+Shift+R で読み込み直す）、次の順に確かめます。論文は公開済みの論文か合成の論文（`demo/demo_paper_ja.pdf`）だけを使います。

| # | 操作 | 期待される結果 |
|---|---|---|
| 1 | 開いた直後 | 右上に「ゲスト（共通デモの閲覧のみ）」と「Googleでログイン」。「論文を解析する」の欄はログインの案内になっている |
| 2 | 一覧の「（デモ）」を開く | デモの解析結果と PDF が見られる |
| 3 | 「Googleでログイン」を押し、大学のアカウントを選ぶ | Google の画面で `@s.okayama-u.ac.jp` なども入力できる（メールアドレスの末尾が固定されない）。SI-NSA に戻り、右上にメールアドレスと「ログアウト」が出る |
| 4 | 論文をアップロードする | 解析が始まり、一覧に出る（デモとは別の論文になる） |
| 5 | **シークレットウィンドウ**か別のブラウザで、別の大学のアカウントでログインする | 4 の論文が見えない。別のアカウントが無いときは、シークレットウィンドウで**ログインせずに**開き、一覧が「（デモ）」だけであることを確かめる |
| 6 | 3 のウィンドウで、開発者ツール（F12）→ Application → Cookies の `mongai_session` の値を1文字書き換え、読み込み直す | 「ログインの有効期限が切れたか…」と表示される。「ゲストに戻る」を押すとゲストになる |
| 7 | もう一度ログインし、右上の「ログアウト」を押す | ゲストに戻り、4 の論文が一覧から消える |
| 8 | もう一度ログインする | 4 の論文が再び見え、解析が続いている（ログアウトしても解析は止まらない） |
| 9 | 個人の Gmail でログインを試す | 同意画面が「内部」なら、Google の画面で「SI-NSA は組織内でのみ利用可能です」と止められる。「外部」なら、SI-NSA の画面に「このGoogleアカウントではログインできません」と表示される |

注意：

- 5 で通常のウィンドウを使うと、Cookie が共有されているため、3 のアカウントのログインが置き換わります（3 のアカウントはログアウトした状態になります）
- 同意画面が「内部」のときは、5 の別のアカウントも同じ組織のアカウントにします（2.2）

確認のあと、サーバーで次を実行すると、結果を確かめられます（トークン・`sub`・メールアドレスの `@` より前は記録していません）。

```bash
docker compose -f compose.yaml logs authn | grep -E "ログイン（|ログインを拒否|受け付けない"
docker compose -f compose.yaml logs auth_proxy | grep -oE "CONNECT [a-z0-9.]+:443" | sort | uniq -c
```

- ログインに成功すると「ログイン（メールのドメイン s.okayama-u.ac.jp）」のような行が出ます
- `auth_proxy` の接続先は `accounts.google.com`・`oauth2.googleapis.com`・`www.googleapis.com` の3つだけのはずです（ほかの宛先があれば報告してください）

### 3.3 リモートのマシン（SSH のポートフォワード）で使う場合

```bash
ssh -N -L 8080:127.0.0.1:8080 <ユーザー名>@<ホスト名>
```

その後、手元のブラウザで **http://localhost:8080** を開きます。

- ログインの Cookie とリダイレクト URI は `localhost:8080` に結び付いています。`http://127.0.0.1:8080` で開いた場合、「Googleでログイン」を押すと自動で `http://localhost:8080` に移ってからログインします
- 手元のポート 8080 が使えず、別のポート（例：18080）で転送する場合は、Google に `http://localhost:18080/auth/callback` を登録し、サーバーの `.env` の `GOOGLE_OAUTH_REDIRECT_URI` も同じ値にします。**全員が同じ手元のポートで転送する必要があります**（リダイレクト URI は1つだけ設定できます）
- `http://localhost` の構成では、Cookie に `Secure` を付けられません。通信は SSH で暗号化されますが、利用者の PC の中では平文です

### 3.4 HTTPS で公開する場合（参考）

`GOOGLE_OAUTH_REDIRECT_URI` を `https://<ホスト名>/auth/callback` にし、Google にも同じ URI を登録すると、Cookie は自動で `Secure` と `__Host-` の接頭辞つきになります。`http://` のリダイレクト URI は `localhost` でしか使えません（`authn` が起動を拒否します）。

> Cloudflare Tunnel など、学外の中継を通す構成では、論文・解析結果が学外を通過します（TODO.md の保留事項）。ログインの導入とは別に判断してください。

## 4. Cookie・セッション・鍵

### 4.1 Cookie

| Cookie | 中身 | 属性 | 期間 |
|---|---|---|---|
| `mongai_session`（HTTPS では `__Host-mongai_session`） | 推測できないランダムな ID（256ビット）だけ | `HttpOnly`・`SameSite=Lax`・`Path=/`・HTTPS では `Secure` | `MONGAI_SESSION_HOURS`（既定8時間） |
| `mongai_login`（HTTPS では `__Host-mongai_login`） | ログインの途中だけ使う、ブラウザの照合用のランダムな値 | 同上 | 10分（ログインが終わると消す） |

- Cookie に、メールアドレス・Google のトークンは入れません。JavaScript からは読めず、URL にも載せません
- 開発用の構成（`make dev`）の `mongai_dev_user` とは名前も仕組みも別です

### 4.2 セッション（`authn_data` ボリュームの `sessions.db`）

- 保存するのは、セッション ID の SHA-256 のハッシュ、Google の発行者と `sub`、メールアドレス、作成・期限・最後の利用の日時だけです。Google のアクセストークン・ID トークンは保存しません
- 期限（既定8時間）か、操作しない時間（既定120分）を過ぎたセッションは無効になり、確認のたびに削除されます
- ログアウトすると、サーバー側でセッションを削除します。Cookie が盗まれていても、ログアウト後は使えません
- ログインのたびに新しいセッション ID を作り、前のセッションを削除します（セッションの固定化の防止）
- 全員を強制的にログアウトさせるには `make authn-revoke-sessions` を実行します
- 許可するドメイン（`MONGAI_ALLOWED_EMAIL_DOMAINS`）を狭めると、範囲外のセッションはその場で無効になります

### 4.3 署名の鍵

- `authn` は、`core` に渡す主張（有効期間60秒の JWT、Ed25519）に署名します。秘密鍵は `authn_data` ボリュームの `signing_key.json`（パーミッション 600、`authn` だけがマウント）に保存し、再起動しても同じ鍵を使います
- 公開鍵は `authn_public` ボリュームの `authn.json` に書き、`core` は読み取り専用でマウントします。`core` には秘密鍵を渡しません
- 鍵の ID は `authn-` で始まります。開発用の `devauth` の鍵（`dev-`）は、本番の構成（`MONGAI_ENV=production`）の `core` が受け付けません
- **鍵の更新（ローテーション）**：`make authn-rotate-key` を実行すると、`authn` を止めて新しい鍵を作り、起動し直します。止めている数秒の間は API が 503（認証サービスに接続できません）になります。`core` は公開鍵のファイルの更新を自動で読み直すので、再起動は不要です。ログイン中のセッションはそのまま使えます（主張は要求ごとに作り直すため）。`authn` を動かしたまま `python -m authn.manage rotate-key` を実行しないでください（再起動までの間、ログイン中の利用者が「有効期限切れ」と表示されます）
- 鍵が漏れた疑いがあるときは、`make authn-rotate-key` と `make authn-revoke-sessions` を続けて実行します

## 5. ログインできないとき（調べ方）

ログインを拒否したときは、画面に理由の分類を表示し、`authn` のログに詳しい理由を記録します。ログには、ID トークン・認可コード・`sub`・メールアドレスのローカル部（`@` の前）は出さず、**クレームの名前、`hd` の値、メールのドメイン、`email_verified` の値**だけを出します。

```bash
docker compose logs authn | grep -E "ログインを拒否|受け付けない"
```

例：

```text
WARNING authn.oidc ログインを拒否：組織のドメイン（hd）が無い（大学の Google Workspace のアカウントではない） {'claims': ['aud', 'azp', 'email', 'email_verified', 'exp', 'iat', 'iss', 'nonce', 'sub'], 'hd': None, 'email_domain': 's.okayama-u.ac.jp', 'email_verified': True}
```

| 画面の表示（`?auth_error=`） | ログの理由 | 考えられる原因と対処 |
|---|---|---|
| このGoogleアカウントではログインできません（`denied`） | メールアドレスのドメインが許可の範囲外 | 個人の Gmail など。大学のアカウントを選び直す |
| 同上 | 組織のドメイン（hd）が無い | 大学のメールアドレスでも、Google Workspace のアカウントでない（Google アカウントを大学のメールアドレスで個人的に作った場合など）。**`claims` に `hd` が無ければ、Google が `hd` を発行していない**。大学の Google Workspace のアカウントでログインしているか確かめる。検証は緩めず、`hd` の発行のされ方を大学の管理者に確認する |
| 同上 | 組織のドメイン（hd）が許可の範囲外 | `hd` の値がログに出ているので、その値が大学の組織のドメインなら `MONGAI_ALLOWED_EMAIL_DOMAINS` への追加を検討する（追加は管理者が判断する） |
| 同上 | メールアドレスが確認されていない | Google 側でメールアドレスが未確認 |
| ログインを確認できませんでした（`failed`） | クレームが不正・署名が不正・認可コードを交換できない | 時刻のずれ（サーバーの時計を NTP で合わせる）、クライアント ID・シークレットの誤り（`invalid_client`）、リダイレクト URI の不一致（`redirect_uri_mismatch`） |
| 手続きの有効期限が切れた（`expired`） | state が一致しない・使用済み・期限切れ | ログインに10分以上かかった、戻るボタンで再送した、`localhost` と `127.0.0.1` を混在させた。もう一度ログインする |
| 認証サービスに接続できませんでした（`unavailable`） | Google と通信できない | サーバーから Google に出られない。`make test-security` の「authn から auth_proxy 経由で Google の OIDC の設定に到達できる」を確かめる |
| ログインが設定されていません（`not_configured`） | — | `.env` の `GOOGLE_OAUTH_CLIENT_ID`・`GOOGLE_OAUTH_CLIENT_SECRET` が未設定 |
| （Google の画面で）`redirect_uri_mismatch` | — | Google に登録したリダイレクト URI と `GOOGLE_OAUTH_REDIRECT_URI` が違う |
| （Google の画面で）メールアドレスの欄の末尾が `@okayama-u.ac.jp` などに固定され、別のドメインを入力できない | — | 認可の要求の `hd` に特定のドメインを指定したときに起きる。SI-NSA は `hd=*` を付けるので通常は起きない。古い `authn` のイメージで動いていないか確かめる（`docker compose up -d --build authn`） |
| （Google の画面で）組織外のため使えない | — | 同意画面の対象が「内部」で、別の組織のアカウント。2.2 を参照 |

## 6. 認証が止まったときの動き

- `authn` が止まっている・セッションの保存先を読めないときは、`/api/` のすべての要求が **503（`auth_unavailable`）** になります。ログインした利用者をゲスト扱いにすることも、ゲストを利用者扱いにすることもありません（フェイルクローズ）。画面には「認証サービスに接続できません」と表示されます
- Google に接続できないときは、新しいログインができません（「認証サービスに接続できませんでした」）。ログイン済みのセッションは、期限までそのまま使えます
- Cookie はあるが無効・期限切れのときは **401（`invalid_session`）** になり、ゲストにはなりません。画面の「もう一度ログイン」か「ゲストに戻る」（Cookie を消す）を選びます
- `.env` の Google の設定を消すと、既存のセッションも無効（401）になります。「ゲストに戻る」で Cookie を消すと、ゲストとして共通デモを閲覧できます

## 7. 無料で使うための前提と制約

- Google Cloud のプロジェクトと、Google でのログイン（OAuth クライアント・OIDC）は無料で使えます。請求先アカウントの設定は不要です。有料の API・サービスは使っていません
- 外部の認証サービス（Auth0・Supabase・Clerk など）や外部のデータベースは使いません。セッションは手元の SQLite に保存します
- 同意画面の対象が「外部」で「テスト中」のときは、テストユーザー（最大100件）だけがログインできます。全員で使うには「公開」が必要です
- Google の方針・画面・無料の範囲は変わることがあります。変更があった場合は Google Cloud Console の表示に従ってください
- 大学の Google Workspace の設定（サードパーティのアプリへのアクセスの制限など）によっては、管理者の許可が必要になる場合があります

## 8. 開発用の構成との関係

- `make dev`（`compose.dev.yaml`）では、従来どおり開発用のモック認証（`devauth`）を使います。`http://127.0.0.1:8080/auth/dev-login?user=alice` でログインします。画面の「Googleでログイン」は alice でのログインに、「ログアウト」は devauth のログアウトになります（Google には接続しません）
- 開発用の構成でも `authn` は起動しますが、`web` は `devauth` に問い合わせ、`core` は `devauth` の公開鍵（`dev-`）だけを受け付けます。鍵・Cookie・セッションは本番の `authn` と別です
- 本番相当の構成（`make up`）には `devauth` が含まれず、`core` は開発用の鍵を受け付けません

## 9. デモ・全学で使うときの設定（学生と教職員の両方が使えるようにする）

開発・動作確認の間は、同意画面の対象を「内部」にしています（2.2）。デモなどで、**学生も教職員も Google でログインするだけで使える**ようにするときは、次のように切り替えます。SI-NSA 側で、メールのドメインと `hd` がどちらも `okayama-u.ac.jp` かそのサブドメインであることを確かめているので、対象を「外部」にしても学外のアカウントは SI-NSA に入れません。

### 9.1 同意画面を「外部」にして公開する

1. Google Auth Platform の「**対象（Audience）**」を開き、ユーザーの種類を「**外部**」に変えます
2. 公開ステータスの「**アプリを公開**」を押し、「**本番環境**」にします
   - 「テスト中」のままだと、「テストユーザー」に登録したアカウント（最大100件）しかログインできません。デモの参加者を一人ずつ登録することになるので、公開します
   - 求めるスコープは `openid`・`email` だけ（機密性の高くないスコープ）なので、通常は Google の審査は不要です。ロゴを登録するとブランドの確認が求められることがあるので、ロゴは登録しません
3. クライアント ID・シークレット・リダイレクト URI はそのまま使えます（変える必要はありません）

### 9.2 大学の Google Workspace の管理者の設定を確かめる

大学の Workspace の管理者が、信頼していない外部のアプリへのログインを制限していると、Google の画面に「アクセスがブロックされました（管理者が承認していません）」と表示されます。学生用と教職員用で設定が違うこともあるので、デモの前に**学生のアカウントと教職員のアカウントを1つずつ**使ってログインを試します。ブロックされた場合は、大学の管理者（情報統括センターなど）に、クライアント ID（`…apps.googleusercontent.com`）を信頼するアプリとして登録するよう依頼します。

### 9.3 参加者が画面を開く経路を決める

| 形態 | リダイレクト URI | 注意 |
|---|---|---|
| 発表者の PC だけで見せる | `http://localhost:8080/auth/callback`（今のまま） | 発表者が SSH でポートを転送する（3.3）。参加者はログインしない |
| 参加者が SSH でポートを転送して使う | 同上 | 全員が同じ手元のポート（8080）で転送する。参加者にサーバーへの SSH の権限が要る |
| 参加者が自分の PC・スマートフォンのブラウザで使う | `https://<公開の URL>/auth/callback`（例：`https://si-nsa.eucaly-labs.net/auth/callback`） | Google の「承認済みのリダイレクト URI」に追加し、サーバーの `.env` の `GOOGLE_OAUTH_REDIRECT_URI` も同じ値にして `docker compose up -d authn` で反映する（Cookie は自動で `Secure` になる）。運用中の Cloudflare Tunnel の経路では論文・解析結果が学外（Cloudflare）を通るため（TODO.md の保留事項）、デモで使う論文は合成論文（`demo/demo_paper_ja.pdf`）などに限る |

`authn` が使うリダイレクト URI は1つだけです。同じサーバーで `localhost` と公開の URL の両方からログインさせることはできません。

### 9.4 デモの前の確認

1. `docker compose logs authn | grep 起動` で、コールバックが 9.3 で決めた URI になっていることを確かめる
2. 学生のアカウントと教職員のアカウントで、それぞれログイン・ログアウトできる（3.2）
3. 個人の Gmail では「このGoogleアカウントではログインできません」と表示される
4. ログインできない場合は第5章の方法で `hd` の値を確かめる

### 9.5 デモの後

参加者のアカウントは、初めてのログインで SI-NSA の利用者として登録されます（論文などのデータは本人だけが見られます）。デモの後に利用を止める場合は、`make authn-revoke-sessions` で全員のログインを無効にし、同意画面を「内部」に戻すか、公開を「テスト中」に戻します。

### 9.6 プロジェクトの持ち主

学生のアカウントで作ったプロジェクトは、卒業などでアカウントが無くなると管理できなくなります。デモの後も使い続けるなら、教職員のアカウントをプロジェクトのオーナーに加えておきます（IAM と管理 → IAM → アクセス権を付与 → ロール「オーナー」）。

## 10. 開発メンバーが自分で動作を確認するとき

### 10.1 Google の設定なしで試せる範囲

| 方法 | 確かめられること | 手順 |
|---|---|---|
| 自動テスト | OIDC の検証（state・nonce・署名・aud・iss・期限・認可コードの再利用など）、許可するドメインの判定、セッション・ログアウト・CSRF、利用者ごとのデータの分離、画面の表示（ゲスト・ログイン中・期限切れ・エラー） | `make test`・`make test-e2e`。偽の Google（`tests/unit/fake_google.py`）を使い、外部とは通信しない |
| ネットワークの分離 | authn・auth_proxy の通信先の制限、ボリューム、nginx の中継 | `make test-security`（実際のコンテナで検証する） |
| 開発用の構成 | 画面の動き（ログイン・ログアウト・ゲスト） | `make dev`。「Googleでログイン」は開発用の利用者 alice でのログインになる（第8章） |

実際の Google のアカウントでしか確かめられないのは、Google の画面での動き、大学のアカウントの `hd` の出方、大学の Workspace の管理者の設定の影響です。

### 10.2 OAuth クライアントとシークレットの扱い

- OAuth クライアントは、SI-NSA を動かす環境（サーバー）ごとに1つの `.env` に設定します。共有のサーバーで試すときは、すでに設定済みの `.env` をそのまま使い、各自で作る必要はありません
- 自分の PC など別の環境で試すときは、第2章の手順で**自分の Google Cloud のプロジェクトに**クライアントを作るのが簡単です（同意画面は「内部」で構いません）
- 既存のクライアントのシークレットを共有するときは、Slack・メール・Issue・チャットの AI ツールに貼らず、サーバー上の `.env` を直接編集してもらうか、パスワード管理ツールなど安全な方法で渡します
- 別の環境で使うリダイレクト URI（例：手元のポートが違う `http://localhost:18080/auth/callback`）は、クライアントの「承認済みのリダイレクト URI」に追加し、その環境の `.env` の `GOOGLE_OAUTH_REDIRECT_URI` も同じ値にします

### 10.3 共有のサーバーで試すときの注意

- Compose のプロジェクト名（`mongai`）とポート（`127.0.0.1:8080`）は固定です。同じサーバーで別のメンバーが自分の clone から `make up`・`make dev` を実行すると、**同じコンテナとボリュームを使い、動いている環境を作り直します**。試す前に、ほかの人が使っていないかを確かめ、試す人を1人に決めます
- 試すブランチは、起動する前に `git branch --show-current` で確かめます
- ボリュームを消すコマンド（`docker compose down -v`・`make clean-data`）は実行しません。止めるときは `docker compose -f compose.yaml down` を使います

### 10.4 結果を報告するとき

- 3.2 の表の番号ごとに、期待どおりかどうか
- うまくいかなかったときは、`docker compose -f compose.yaml logs authn | grep -E "ログインを拒否|受け付けない"` の行（`hd`・メールのドメインなどの安全な属性だけが出る）と、画面のスクリーンショット
- スクリーンショットや貼り付けには、クライアント シークレット（`GOCSPX-…`）、`.env` や JSON の中身、未発表の論文の内容を含めない。アドレスバーの `code=`・`state=` は1回しか使えない値なので、写っていても問題ない
